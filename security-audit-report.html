Critical Hardcoded Database Password in Schema
📁 prisma/schema.prisma, .env.example
📍 Location

prisma/schema.prisma line 7, .env.example line 2

⚠️ Description

The database connection string in .env.example contains a hardcoded password (password) that could be accidentally committed or used in production. Additionally, the Prisma schema uses SQLite which is not recommended for production applications. 

DATABASE_URL="postgresql://postgres:password@localhost:5432/nakis?schema=public"
💥 Impact
  • Default credentials may be used in production deployments
  • Attackers could gain direct database access
  • Data breach, data manipulation, or complete data loss
✅ Recommendation:
  1. Remove hardcoded password from .env.example and use placeholder like YOUR_SECURE_PASSWORD
  2. Enforce strong password generation for production databases
  3. Use environment-specific secrets management (Vercel Env, AWS Secrets Manager, etc.)
  4. Consider migrating from SQLite to PostgreSQL for production (already referenced but schema uses SQLite)
Critical SQLite Database in Production Environment
📁 prisma/schema.prisma
📍 Location

prisma/schema.prisma line 5

datasource db {
  provider = "sqlite"
  url      = "file:./dev.db"
}
⚠️ Description

The application uses SQLite as the database provider, which is stored as a file (./dev.db). This is inappropriate for production because:

  • SQLite lacks proper user authentication and access control
  • File-based database can be easily exfiltrated if server is compromised
  • No support for row-level security or granular permissions
  • Concurrent write operations can cause locking issues
  • The .env.example references PostgreSQL but schema uses SQLite (inconsistency)
💥 Impact
  • Database file can be directly accessed if server is compromised
  • No proper access control at database level
  • Performance and reliability issues in production
✅ Recommendation:
  1. Migrate to PostgreSQL for production (update schema.prisma provider)
  2. Update Docker configuration to include PostgreSQL container
  3. Ensure database file is not accessible via web server
  4. Implement proper database backup and encryption at rest
High Insufficient File Type Validation on Upload
📁 src/app/api/files/upload/route.ts
📍 Location

src/app/api/files/upload/route.ts lines 38-48

⚠️ Description

File upload validation only checks file extension but does not validate MIME type or file content. An attacker could upload a malicious file with a valid extension (e.g., malicious.php.jpg) or rename any file to have an allowed extension. 

// Only extension is checked
const ext = file.name.split('.').pop()?.toLowerCase();
if (!ext || !ALLOWED_EXTENSIONS.includes(ext)) {
    return NextResponse.json({ error: `File type .${ext} is not allowed.` }, { status: 400 });
}
💥 Impact
  • Malicious file upload (web shells, malware)
  • XSS attacks via uploaded SVG/HTML files
  • Server compromise if uploaded files are executable
✅ Recommendation:
  1. Validate MIME type using file.type property
  2. Use a library like file-type to validate file content via magic bytes
  3. Store uploaded files outside webroot with no execute permissions
  4. Implement virus scanning for uploaded files
  5. Consider using Cloudflare R2 or S3 with proper bucket policies
High Exposed Supabase Service Role Key in Environment
📁 .env.example, src/lib/supabase.ts
📍 Location

.env.example line 8

SUPABASE_SERVICE_ROLE_KEY="your-supabase-service-role-key"
⚠️ Description

The Supabase service role key provides full administrative access to the Supabase backend including all tables, authentication, and storage. If this key is exposed (via client-side code, logs, or repository), attackers gain complete control.

💥 Impact
  • Complete database access and manipulation
  • User data exfiltration
  • Authentication bypass
  • Storage bucket manipulation
✅ Recommendation:
  1. Never expose service role key in client-side code
  2. Use Supabase anon key for client operations with RLS policies
  3. Rotate service role key immediately if ever exposed
  4. Consider if Supabase is necessary given Prisma is the primary ORM
High Password Reset Token Not Invalidated After Use
📁 src/app/api/auth/reset-password/route.ts
📍 Location

src/app/api/auth/reset-password/route.ts

⚠️ Description

After a successful password reset, the token should be immediately invalidated to prevent reuse. The current implementation may not properly clear the token in all code paths, potentially allowing token replay attacks.

💥 Impact
  • Password reset token reuse
  • Account takeover if token is intercepted
  • Multiple password changes from single token
✅ Recommendation:
  1. Ensure resetPasswordToken and resetPasswordExpires are set to null immediately after successful reset
  2. Implement one-time-use token validation
  3. Add logging for password reset attempts
Medium Rate Limiting Bypass via X-Forwarded-For Spoofing
📁 src/lib/rate-limit.ts
📍 Location

src/lib/rate-limit.ts lines 43-50

export function getClientIP(request: Request): string {
    const forwardedFor = request.headers.get("x-forwarded-for");
    if (forwardedFor) {
        return forwardedFor.split(",")[0].trim();
    }
    ...
}
⚠️ Description

The getClientIP function trusts the X-Forwarded-For header without validation. Attackers can spoof this header to bypass rate limiting by rotating through fake IP addresses.

💥 Impact
  • Rate limiting bypass
  • Brute force attacks on authentication
  • Resource exhaustion attacks
✅ Positive Note: Rate limiting is implemented with rate-limiter-flexible, but IP extraction needs hardening.
✅ Recommendation:
  1. Only trust X-Forwarded-For from known proxy IPs (Cloudflare, nginx)
  2. Use X-Real-IP when behind a trusted reverse proxy
  3. Implement Cloudflare's CF-Connecting-IP header validation
  4. Consider using middleware-level IP extraction from trusted sources only
Medium Potential Path Traversal in File Download
📁 src/app/api/files/[id]/route.ts
📍 Location

src/app/api/files/[id]/route.ts lines 54-72

⚠️ Description

File paths are constructed using join() which prevents basic path traversal, but the filename is derived from database-stored file.url. If an attacker can inject path components into the database, they could potentially access files outside the intended directory.

💥 Impact
  • Unauthorized file access
  • Information disclosure
  • Potential code execution if sensitive files are read
✅ Positive Note: Authorization checks are properly implemented before file access.
✅ Recommendation:
  1. Validate that resolved path is within expected directory using realpath()
  2. Sanitize filename to remove any path components
  3. Use UUID-based filenames only (already implemented)
  4. Add additional validation on file.url before use
Medium Incomplete CSRF Protection Coverage
📁 src/middleware.ts
📍 Location

src/middleware.ts lines 34-65

⚠️ Description

CSRF protection in middleware checks Origin/Referer headers for API routes, but NextAuth built-in routes are excluded. While NextAuth has its own CSRF protection, custom authentication endpoints (register, forgot-password, reset-password) should also implement CSRF tokens for defense-in-depth.

💥 Impact
  • Cross-site request forgery on auth endpoints
  • Account creation spam
  • Password reset abuse
✅ Positive Note: Origin/Referer validation is implemented for state-changing requests.
✅ Recommendation:
  1. Add CSRF tokens to all state-changing endpoints
  2. Use NextAuth's built-in CSRF token for custom endpoints
  3. Implement SameSite cookie attributes
  4. Consider double-submit cookie pattern for API routes

Low Missing Permissions-Policy Header
📁 next.config.ts
📍 Location

next.config.ts headers configuration

⚠️ Description

The application sets several security headers but could benefit from additional headers like Permissions-Policy to control browser features, and Cross-Origin-Embedder-Policy for enhanced isolation.

💥 Impact
  • Reduced defense-in-depth
  • Potential side-channel attacks (Spectre-style)
✅ Positive Note: Comprehensive security headers are already implemented including CSP, HSTS, X-Frame-Options.
✅ Recommendation:
  1. Add Permissions-Policy: camera=(), microphone=(), geolocation=()
  2. Consider adding COEP and COOP headers for cross-origin isolation
  3. Implement X-Permitted-Cross-Domain-Policies
Low Missing Account Lockout After Failed Attempts
📁 src/lib/auth.ts
📍 Location

src/lib/auth.ts credentials authorize callback

⚠️ Description

While rate limiting is implemented at the API level, there's no account-level lockout after consecutive failed login attempts. An attacker could target specific accounts with brute force attacks.

💥 Impact
  • Targeted brute force attacks on specific accounts
  • Credential stuffing attacks
✅ Positive Note: IP-based rate limiting is implemented (5 attempts per 15 minutes).
✅ Recommendation:
  1. Implement account lockout after N failed attempts
  2. Add progressive delays between login attempts
  3. Notify users of suspicious login activity
  4. Consider implementing CAPTCHA after failed attempts
